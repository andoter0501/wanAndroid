# 玩 Android HarmonyOS 项目开发经验总结

本文整理了本项目开发过程中遇到的主要问题、原因判断、处理方式和后续经验，方便后续迭代时快速定位同类问题。

## 1. ArkTS 编译报组件方法不存在

**问题现象**

`HomePage.ets` 编译时报错：

- `Property 'sectionTitle' does not exist on type 'HomePage'`
- `Property 'homeArticleCard' does not exist on type 'HomePage'`
- `does not meet UI component syntax`

**原因**

页面模板中调用了 `this.sectionTitle()`、`this.homeArticleCard()`，但对应 `@Builder` 方法未实现或方法名不一致。ArkUI 对 UI 组件语法比较严格，缺失 Builder 会同时触发类型错误和 UI 语法错误。

**处理方式**

补齐页面内 Builder 方法，并复用已有 `ArticleCard` 组件，保证调用方式符合 ArkUI 组件语法。

**经验**

ArkTS 页面报 “does not meet UI component syntax” 时，不要只看语法本身，也要检查被调用的 Builder 是否存在、是否有 `@Builder` 标记、参数类型是否明确。

## 2. 项目和广场卡片文字未左对齐

**问题现象**

项目列表、广场列表中卡片文字看起来居中或对齐不统一。

**原因**

卡片内部 `Text` 或父级 `Column` 没有明确设置 `textAlign(TextAlign.Start)` 和 `alignItems(HorizontalAlign.Start)`。

**处理方式**

在卡片标题、描述、元信息上统一补充左对齐约束，并确保卡片父容器按左对齐布局。

**经验**

ArkUI 中父容器和文本自身都可能影响视觉对齐。处理列表卡片时，应同时检查父级 `alignItems` 和子级 `textAlign`。

## 3. 体系二级分类点击无内容

**问题现象**

体系页部分二级分类点击后没有效果，无法查看对应分类文章。

**原因**

页面只展示了树形分类，没有按 WanAndroid 官方接口加载分类文章：

`/article/list/{page}/json?cid={cid}`

**处理方式**

在点击二级分类时调用分类文章接口，从第 0 页开始加载；进入分类文章列表后，文章点击打开 Web 详情页。

**经验**

接口文档中的 `cid` 是二级分类 id，不是一级分类 id。分页从 0 开始，后续如果传入 `page_size`，必须每页都传，避免分页错乱。

## 4. 顶部标题返回键显示不合理

**问题现象**

当前 Tab 根页面也显示返回键，看起来像子页面。

**原因**

标题栏没有区分“Tab 根页面”和“Tab 内子页面”。

**处理方式**

根页面不显示返回键；进入体系二级分类文章列表等子页面后才显示返回键。

**经验**

移动端 Tab 架构下，返回键应表达页面层级，而不是简单按标题栏复用。根 Tab 不应显示返回键。

## 5. 收藏功能不完整

**问题现象**

收藏入口、取消收藏、我的收藏列表和登录态之间联动不完整。

**原因**

WanAndroid 收藏接口都要求登录，并且“文章列表取消收藏”和“我的收藏页取消收藏”的接口不同：

- 列表页取消收藏：`/lg/uncollect_originId/{id}/json`
- 我的收藏页取消收藏：`/lg/uncollect/{id}/json`，需要 `originId`

**处理方式**

完善收藏服务：

- 收藏前检查登录态。
- 登录失效时清空本地会话和收藏状态。
- 我的收藏页使用对应取消收藏接口。
- 收藏状态通过 `FavoriteService` 在页面间同步。

**经验**

收藏功能不能只看一个接口，要按触发位置区分取消收藏方式。登录 Cookie 需要持久化，否则接口会频繁返回未登录。

## 6. 我的收藏卡片展示不清晰

**问题现象**

收藏列表 Item 信息层级不清楚，类型位置不明显，文字对齐不好。

**原因**

收藏文章的分类、标题、作者、时间和取消收藏动作没有形成清晰的信息结构。

**处理方式**

重新设计收藏卡片：

- 标题左对齐。
- 分类标签使用 `superChapterName / chapterName`。
- 取消收藏按钮放到更明确的位置。
- 卡片内容按标题、元信息、分类分层。

**经验**

收藏列表是用户管理型页面，信息密度可以比首页更高，但标题、类型和操作按钮必须有稳定位置。

## 7. 列表缺少刷新能力

**问题现象**

首页、体系文章、项目、广场、收藏、搜索等列表都只能首次加载或加载更多，没有下拉刷新。

**原因**

通用分页组件只封装了状态、重试和加载更多，没有封装 `Refresh`。

**处理方式**

在 `PagedListView` 中封装刷新能力，增加 `refreshAction`，各页面传入自己的刷新逻辑。

**经验**

下拉刷新应放在通用分页组件中统一处理，避免每个列表重复实现。刷新逻辑必须和“首次加载”区分，避免破坏分页状态。

## 8. 首页问答替换为常用网站

**问题现象**

首页原先展示问答内容，需求调整为展示常用网站接口：

`/friend/json`

**处理方式**

增加常用网站接口、数据模型和 ViewModel 字段，在首页展示常用网站入口。

后续又按需求过滤：

- 只保留 `category = 博客`
- 保留 Android 官网
- 去掉 `外文翻译`
- 增加掘金 Android 和掘金 AI 入口

**经验**

接口返回内容较多时，首页展示要有明确筛选规则。筛选逻辑应集中在页面方法中，避免散落在 UI 多处。

## 9. 快捷方式和我的页 TODO 清理

**问题现象**

首页快捷方式中有不再需要的“常用网站”“路线”；我的页面存在 TODO 项。

**处理方式**

移除无效快捷入口和 TODO 菜单项，同时删除相关无用样式判断。

**经验**

原型阶段留下的入口如果不清理，会让用户误以为功能未完成。菜单项必须对应真实功能。

## 10. 我的页面个人数据不真实

**问题现象**

我的页积分、排名、收藏数显示为空或占位。

**原因**

最初只读取了登录接口或旧字段，没有完整解析用户信息接口：

`/user/lg/userinfo/json`

真实数据可能来自：

- `coinInfo.coinCount`
- `coinInfo.level`
- `coinInfo.rank`
- `collectArticleInfo.count`
- 兜底字段：`userInfo.coinCount / level / rank / collectIds`

**处理方式**

扩展用户信息模型，并在登录成功后立即拉取用户信息，写入本地 session。我的页优先读接口状态，接口状态未刷新时读 session 兜底。

**经验**

用户信息页不要只依赖登录接口。登录成功后应主动拉取一次完整用户资料，避免页面生命周期未触发时数据缺失。

## 11. 我的页数据只有数字，含义不清楚

**问题现象**

积分、排名、收藏只显示数字，用户不知道数字含义。

**处理方式**

将数据区优化为更明确的指标展示，数字和标签同时展示；后续又按参考图调整成三列统计卡。

**经验**

个人中心的数据展示要避免“裸数字”。数字旁边必须有明确标签，例如积分、排名、收藏。

## 12. 我的页 UI 按示例图还原后比例过大

**问题现象**

参考图样式套用后，统计卡、菜单行、图标、文字整体过大，不符合当前项目页面比例。

**原因**

示例图是截图像素比例，不能直接映射到当前 ArkUI 设计尺寸。

**处理方式**

保留示例图结构，但将尺寸回调到原页面量级：

- 统计卡高度从大尺寸回调到紧凑尺寸。
- 菜单行高度、图标块、字号都缩小。
- 恢复顶部头像、昵称、等级排名区域。

**经验**

UI 还原要先还原结构，再按项目现有设计系统调尺寸。不能直接照搬截图像素。

## 13. 切换 Tab 时重复请求网络

**问题现象**

每次切换 Tab 都重新请求网络，页面感觉很慢。

**原因**

`AppShellPage` 使用 `if (currentTab === ...)` 条件渲染当前 Tab。切走时页面被销毁，切回来重新创建，导致 `aboutToAppear()` 再次触发请求。

**处理方式**

改成访问过的 Tab 保持挂载：

- 首次进入某个 Tab 时创建页面。
- 后续切换只通过 `Visibility.Visible / Hidden` 控制显示。
- 手动刷新、重试、分类切换仍然正常请求网络。

**经验**

Tab 页面应缓存实例，避免条件渲染导致频繁销毁重建。尤其是首页、项目、广场这类网络列表页。

## 14. 系统设置为空

**问题现象**

我的页中“系统设置”没有实际功能。

**处理方式**

新增系统设置页，内容保持精简：

- 清除本地缓存。
- 关于应用。
- 源代码地址。
- 个人联系方式。
- 隐私协议。

清除本地缓存只清搜索历史和本地收藏状态，不清登录 Cookie，避免误退出。

**经验**

设置页第一版不宜功能过多。先做稳定、低风险、高感知的功能，再逐步扩展主题、字体、列表密度等体验配置。

## 15. 设置页顶部出现大空白

**问题现象**

系统设置页标题栏下方到“本地数据”卡片之间出现大块空白。

**排查过程**

先怀疑是通用 `PageHeader` 组件底部灰色分隔条和内容 top padding，去掉后仍有空白。根据截图继续排查后发现，问题来自 `Scroll + Column` 在当前页面布局下没有按预期从顶部排列，内容被放到了可视区偏中部。

**处理方式**

将设置页主体从：

```arkts
Scroll() {
  Column() { ... }
}
```

改为：

```arkts
List() {
  ListItem() { ... }
}
```

**经验**

设置项列表更适合用 `List`。如果 `Scroll + Column` 出现垂直居中或空白异常，应优先检查父容器约束和滚动容器布局机制，而不是只调 padding。

## 16. `.appanalyzer` 目录进入版本管理

**问题现象**

DevEco 生成的 `.appanalyzer/` 出现在 Git 未跟踪文件中。

**处理方式**

确认该目录未被 Git 跟踪后，将 `.appanalyzer/` 加入 `.gitignore`。因为未被跟踪，所以不需要执行 `git rm --cached`。

**经验**

处理忽略文件时要先判断是否已被 Git 跟踪：

- 未跟踪：只加 `.gitignore`。
- 已跟踪：需要 `git rm --cached` 从索引移除，但保留本地文件。

## 17. hvigor 构建环境问题

**问题现象**

构建过程中遇到过：

- hvigor daemon lock 异常。
- `DEVECO_SDK_HOME` 无效。
- 大量 deprecated warning。

**处理方式**

对 lock 问题，清理残留 lock 后重试。对 SDK 路径问题，显式指定：

```shell
DEVECO_SDK_HOME=/Applications/DevEco-Studio.app/Contents/sdk
```

deprecated warning 暂不扩大处理，避免和当前功能改动混在一起。

**经验**

构建失败要区分“环境问题”和“代码问题”。只有进入 `CompileArkTS` 后的错误才通常是代码问题；daemon、SDK 路径、lock 多半是环境问题。

## 18. ArkTS 开发规则沉淀

**关键规则**

- 不使用 `any / unknown`，尽量定义明确接口。
- `catch` 中使用明确变量并通过 `parseErrorMessage` 归一化错误。
- UI Builder 方法必须符合 ArkUI 语法，避免高阶 Builder 写法不兼容。
- 数据模型要尽量和接口字段端到端对应，同时给服务端缺字段留兜底。
- 修改 UI 后必须跑 `assembleHap` 验证。

**经验**

ArkTS 编译器对 UI DSL 的限制比普通 TypeScript 更严格。实现前先读周边代码风格，尽量复用已有组件和模式。

## 19. 和 AI 协作时有效的提示语

**沟通方式**

这次协作中，比较有效的提示方式不是一次性写很长需求，而是持续给出具体问题、现象、参考资料和反馈。例如：

- 给出完整编译日志：直接贴 hvigor 报错，能快速定位 ArkTS 编译问题。
- 给出官方接口说明：例如体系分类、收藏、用户信息、常用网站接口，能减少接口字段猜测。
- 明确当前问题现象：例如“很多二级子名称点击没效果”“还是没有显示数据”“切换 tab 页会主动请求网络”。
- 给出 UI 参考图：例如 `doc/111.png` 和 `doc/re.jpg`，比抽象描述更容易对齐视觉问题。
- 及时指出偏差：例如“整体都太大了”“头像那块还要保持跟原来一样”“中间还是有很大的空地方”。
- 明确范围边界：例如系统设置只做“清缓存、关于、源代码地址、联系方式”，避免功能扩散。

**推荐提示语模板**

后续继续开发时，可以使用下面这些表达方式：

```text
这是当前报错日志：...
请先判断原因，再做最小修改，并跑构建验证。
```

```text
这个页面的 UI 参考图在 doc/xxx.png，结构照参考图，但尺寸要保持项目现有比例。
```

```text
这个接口说明如下：...
请按接口字段补模型、请求、页面展示和空值兜底。
```

```text
现在现象是：...
我期望的效果是：...
不要改动其它无关功能。
```

```text
这个功能只做这些项：...
不要加入额外设置或复杂能力。
```

**经验**

和 AI 协作时，最有效的信息是“现象 + 参考资料 + 期望结果 + 范围边界”。如果发现实现偏差，直接指出偏差点，比泛泛说“不对”更容易快速收敛。

## 总体经验

1. 先定位真实原因，再改 UI 数值。很多视觉问题不是 padding，而是容器布局机制。
2. 网络列表页要区分首次加载、手动刷新、加载更多和 Tab 缓存。
3. 涉及登录态的接口要同时考虑 Cookie、session、本地缓存和失效事件。
4. UI 参考图只能作为结构参考，尺寸要回到项目设计比例。
5. 每次 ArkTS 改动后都应扫描规则并跑 hvigor 构建，避免小改动引入编译失败。
6. 和 AI 协作时，优先提供完整日志、接口文档、截图路径和明确范围，能显著减少返工。
